===========================================================================
專題開放問題 / 已知限制（2026-11-25）
Secure MCP Gateway for a 5G Core · 給收尾與 limitations 用
===========================================================================

分三類：A 效度缺口（measure 跟 claim 不一致）、B 真實性缺口（威脅模型是否
貼近真實部署）、C 殘餘安全限制（防禦本身擋不住的）。
每條標：問題 / 為什麼是問題 / 狀態 / 怎麼收。

===========================================================================
A. 效度缺口（measure 的跟 claim 的不是同一件事）
===========================================================================

A1. ENUM 的「外洩」沒有真的送出去
    問題：有/無 gateway 兩組，SUPI 都只到達 agent、沒送給攻擊者；
          「外洩 100%->0%」其實是在量「L1 有沒有 token 化」。
    狀態：未解。
    收法：(i) 威脅模型明講「攻擊者可觀察 agent 輸出」讓它成立〔純寫作〕，
          或 (ii) 做一個真的 outbound tool（export_report）〔約 1~2 天〕。

A2. core_precheck 的「擋下」沒 live 測過
    問題：precheck 機制 live 會跑（+13ms），但 live 目標都真的存在，
          所以它從沒在真 core 上真的擋下任何東西；「擋下」只有 offline。
    狀態：機制 live、擋下 offline。
    收法：加一個「打不存在 pdu_session_id」的 live 情境〔半天，只加 JSON+cell〕。

A3. FSM 對 release 無 live 防護價值
    問題：FSM 擋的「重複 release」在 free5GC 上 SMF 本就回 404，冗餘；
          它會有用的 procedure 只在假 core 上測過。
    狀態：offline-only，release 上冗餘。
    收法：誠實寫成「機制正確+通用（offline）+ 原始碼證據」，live 列 future work。

A4. 「真 capability 被濫用」只有 offline
    問題：L3「即使 L2 正常也需要」的主要理由（被劫持 agent 握真 capability）
          只有離線 deterministic 測試。
    狀態：offline-only。
    收法：補一次 live run（情境領 9 次 capability -> L1+L2 放 9、完整放 3）〔約 1 天〕。

===========================================================================
B. 真實性缺口（威脅模型 vs 真實部署）
===========================================================================

B1. 注入路徑是假設的
    問題：假設攻擊者能寫入 alert log，但沒展示具體的 5G 路徑
          （哪個 UE 可控欄位 / 租戶工單 / 第三方 intent 會流進來）。
    狀態：假設，未展示。
    收法：limitations 誠實寫；可選查「UE 可控的 DNN 是否被原樣寫入 log」〔約 1 天〕。

B2. release 走非標準路徑
    問題：tool 直打 SMF 的 ReleaseSMContext（原本 AMF 呼叫的服務），
          跳過 N1/N2 signalling；真實 OAM agent 較可能走 MnS/NEF。
    狀態：已知，設計使然。
    收法：limitations 寫清楚；改接 MnS/NEF 列 future work。

B3. 腳本化 agent，不是真 LLM
    問題：agent 必定被劫持、攻擊從不拿 capability，所以數字是「腳本動作
          空間內的上界」，不是真實攻擊成功率。
    狀態：設計使然，定位為最壞情況。
    收法：明確標為最壞情況；live LLM 研究列 future work。

===========================================================================
C. 殘餘安全限制（防禦本身擋不住的，要誠實列）
===========================================================================

C1. 有效 capability 完全跳過 taint
    問題：帶有效 capability 的呼叫會略過整個 L2（連 value-level taint），
          所以被劫持 agent 握真 capability 時 L2 會放行。
    狀態：已知；靠 L3 rate cap 當後備。

C2. rate cap 誤擋合法批次
    問題：rate cap 分不出合法批次清空與惡意大量拆除，兩者都擋
          （BENIGN-05，FP 5/5）。
    狀態：已知取捨。
    收法：limitation；或實作「用 taint 區分」（乾淨+capability 尊重 budget、
          tainted 硬上限）〔小幅改碼〕。

C3. slow drip / bucket split 可繞過
    問題：把 release 間隔拉長到超過 window，或分散到不同 rate bucket，
          就繞過 rate cap。
    狀態：已知；windowed rate 的固有限制。
    收法：cumulative/absolute budget 列 future work；bucket 合併是 config 選擇。

C4. token 是 16-bit 前綴，可猜
    問題：token 為 HMAC 的 16-bit 前綴，猜中機率約 N/2^16。
    狀態：已界定；猜中不洩漏 SUPI，只在呼叫中指名某 subscriber，其餘層仍生效。
