  狀態為準」這套機制，不是單一攻擊的防禦。

四、追問備答
===========================================================================
Q：L2 不就是「讀過 log 就鎖、有 ticket 才放」？
  承認：live 擋下全是 session 級 taint，value-level 只 offline。精確說「session 級
  provenance + 自簽 capability」；粗粒度是因為 agent 是黑盒。

Q：乾淨 session（沒讀 log）不帶 capability 也能 release？
  對。threat model 假設指令只從被標記的 untrusted source 進來。補強：high-risk 一律
  要 capability（這點跟「agent 已完全攻陷」有點矛盾，建議自己先講）。

Q：precheck/FSM 核網自己就會擋，L3 有什麼用？
  對 release 確實無額外防護（重複 release 本就 404）。L3 live 的防護增益只有 rate cap；
  core_precheck 是機制正確性的 live 示範。這也是為什麼主力擺 L1+L2。

Q：L3 是不是只有 FSM 沒 live？
  對。rate cap（DOS-02）、core_precheck（DOS-03）都 live，只有 FSM 順序防護是 offline。
  core_precheck live 歸 live，但它那格「沒 gateway 也不會造成傷害」，所以是機制示範、
  不是防護增益。

Q：為什麼選 SMF 當 release 介面？
  SMF 的 ReleaseSMContext 是核網端真正 teardown（刪 UPF N4/PFCP + PCF/UDM），不必驅動
  UE。選它因 (1) 可得 ground truth（204 + 探測 404），(2) free5GC 上最小可達 REST 端點。
  代價：真正呼叫者其實是 AMF、真實 OAM 較可能走 MnS/NEF —— 已列 limitation。

Q：capability 濫用是指什麼？
  被劫持 agent 握一張真的、gateway 簽的 capability。它只綁「工具+次數」、不綁目標/意圖；
  operator 為維護窗口發「可釋放 9 次」，agent 被注入後 L2 每次都放行（真憑證、分不出），
  只剩 L3 rate cap 把損害壓到 3。= 「L2 正常也擋不住、所以需要 L3」的案例。

Q：若真實要走 NEF，攻擊走 SMF 的防禦還有價值嗎？
  有，且與介面無關。gateway 檢查的是呼叫語意（釋放哪個 session）與核網真實狀態，不是
  傳輸介面。路徑若是 NEF，工具改呼叫 NEF，四個檢查照跑。SMF vs NEF 只影響「示範的
  真實性」（limitation），不影響機制成立；直打 SMF 是為拿最直接的 ground-truth teardown。

===========================================================================
我們的落點：L1+L2 全 live、L3 rate+precheck live、FSM/capability 濫用 offline+標註、
  外洩用假設、注入路徑與 SMF 非標準路徑列 future work。誠實、完整度高。
最大困難（都指向「補 live 要新建工具/procedure」，是工程時間）：

  2. free5GC 架構：重複 release 只回 404，FSM 順序防護要 live 就得另建 procedure。
  3. 真實性路徑：release 直打 SMF，貼近真實要改 MnS/NEF。
