參考 B：老師可能追問，先備好答案
===========================================================================
Q：為什麼選 SMF 當 release 介面？
  A：SMF 的 ReleaseSMContext 是核網端真正的 teardown（刪 UPF N4/PFCP + PCF/UDM
     狀態），是 network-initiated release，不必驅動 UE 就真的拆掉 session。選它
     因為 (1) 可得 ground truth：SMF 204 + 事後探測 404 雙重確認；(2) 是 free5GC
     上最小可達的 REST 端點，不必另架 NEF/MnS。代價：真正的呼叫者其實是 AMF，
     真實 OAM 較可能走 MnS/NEF —— 已列為 limitation（B2）。

Q：capability 濫用是指什麼？
  A：被劫持的 agent 手上握著一張「真的、gateway 簽發的」capability。capability 只
     綁「工具+次數」，不綁目標或意圖；operator 為維護窗口發一張「可釋放 9 次」的
     憑證，agent 一旦被注入，L2 會放行每一次（它是真憑證，L2 分不出），只剩 L3 的
     rate cap 把損害壓到 3。這是「即使 L2 正常也擋不住、所以需要 L3」的案例，目前
     只有 offline 驗證（對應 Q2）。

Q：攻擊走 SMF API，若真實要走 NEF，防禦還有價值嗎？
  A：有，且價值與介面無關。gateway 檢查的是「工具呼叫的語意」（要釋放哪個 session）
     與「核網真實狀態」，不是某個傳輸介面。真實路徑若是 NEF，工具就改呼叫 NEF，
     同樣四個檢查照跑：L1 token 化、L2 taint+capability、L3 rate、core_precheck
     （它查的是 AMF/WebConsole 的 session 狀態，本就與 release 走 SMF 或 NEF 無關）、
     FSM。換言之 SMF vs NEF 只影響「示範的真實性」（B2 limitation），不影響機制是否
     成立。我們直打 SMF 是為了在 free5GC 上拿到最直接的 ground-truth teardown。
